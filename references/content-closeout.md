# 发布后资料回流

每次实际提交或发布后，先持久记录每个平台真实状态、原生 ID、已核公开链接和版本，再做资料同步。`submitted` 不等于 `published`；管理页不是公开作品地址。未知最终结果先对账，不重新投递。

在提供 `scripts/content_sync.py` 的 Moonlit 内容工作区中，读取该工作区的 `maintenance/CONTENT-SYNC.md` 并执行其完整流程：

1. 发布记录用作品 CLI 登记；`content_sync.py scan --work W-ID` 从同版最终字幕登记最终逐字稿，不覆盖原始识别稿或写作稿。
2. 以稳定 ID 关联已有 Notion 选题，准备受管作品页；正式 MCP 写入后真实 fetch 读回正文、逐字稿、版本及逐平台状态。历史缺证据条目留 blocked，不按相似标题盲建。
3. 读取现有选题属性、按计划推进状态并追加发布引用；保留人工编辑和原稿链接。选题“已发”表示存在已公开平台，不能抹掉其他平台待审。读取富文本属性用 fetch/rows，不能把 SQL 丢失链接目标误判为空。
4. 正文及选题分别读回均通过才确认 Notion 已同步。官方发布时间未知不拿 observedAt 填日期。
5. 用户已配置且授权的私有远端，通过现有数据工具按作品 ID 导出受管投影、定向提交推送并读回。凭据和媒体不随包外传；没有对应远端或授权则报告该项未接入，不擅建公开仓库。
6. 重新读取本地看板和持久队列；同步失败保留 pending/blocked/unknown 和下一步，仅重试同步，不重传视频。

工作区 CLI 是资料状态所有者，正式 Notion MCP 是传输通道，私有远端是投影。未接入该工作区合同的普通安装，按其自身配置记录等价回执，不假称已实现自动 Notion/Git 同步。平台发布成功、Notion 成功、远端推送成功和看板读回必须分别报告。

同步授权不是下一部作品的发布许可。没有新凭据需求就不用读取秘密；需要时按用户密钥来源规则执行。
